# Project decisions - ReverseHire (candidate side)

Last updated: 2026-11-18 (see "Decisions of 2026-11-12", "Decisions of 2026-11-17" and "Decisions of 2026-11-18" at the end: they supersede some older rows, which are kept and marked). Supporting research notes are kept outside the repository (the `fonti/` folder is git-ignored and never published).
## What we are building

A Python desktop application that works "backwards" compared with the usual hiring tools: it starts from **one CV** and finds, in a geographic area, **the companies that fit that profile**, highlighting the ones that are **hiring**.

Visible name: **ReverseHire** (brand 0THack1A, first character the digit zero). The Python package is called `reversehire`.

## Constraints and rules to respect

- **Nominatim**: at most 1 request per second, identifying User-Agent, caching required.
- **Overpass**: moderate use, results cached; only a fallback (decision F4).
- **Crawling**: respect robots.txt, a delay between requests to the same site, few pages per company, declared User-Agent. Parallel crawling (decision C1) never relaxes these rules.
- **Excluded sources**: no scraping of LinkedIn, Indeed, Glassdoor (terms of use). **Superseded by N2**: Indeed and LinkedIn are accepted as an optional source, off by default; Glassdoor is still not read.
- **Privacy**: the CV stays on the computer. With Firecrawl only company URLs are sent, never the CV. With MCP the CV content may reach the model: this must be disclosed to the user.
- **Attribution**: "© OpenStreetMap contributors" (ODbL) visible in the app; ESCO terms to be verified.
- **Transparency**: every score shows its evidence; the app states that the company list is incomplete.

## Accepted known limits

- OpenStreetMap is not a company register: many small companies are missing or have no website listed. Large companies without map tags can rank low or be missing unless a register list is imported.
- The role -> sector/OSM tag map has to be built by hand and is the most delicate part.
- Without an LLM, requirement extraction from free-text postings will be approximate.
- A "culture/values" score from the website alone is unreliable: not included in the first version.

**Note on B4.** The absence of fixed limits concerns the user's choices, not the rules of the external services, which stay mandatory: 1 request per second to Nominatim, moderate use of Overpass, delays between requests to the same site. Consequently:

- before starting, the app shows an **estimate** of companies found and expected time, asking for confirmation if the search is long;
- very large radii are split into several Overpass queries so as not to exceed the server's time limits;
- the search can be **cancelled and resumed**, and partial results are saved;
- companies are processed in order of estimated relevance, so useful results arrive first.

| # | Topic | Decision | Reason / note |
|---|---|---|---|
| G1 | GUI toolkit | Moved from tkinter (the original choice in D2) to **Qt via PySide6**. Themes: dark, light, or follow the system. Bundled font: JetBrains Mono (SIL OFL 1.1) | Better look and theming; no change to the core. PySide6/Qt is LGPL-3.0, see `ATTRIBUTIONS.md` |

| C1 | Parallel search | The search visits several company sites **in parallel**; the number is user-settable (default 8). `robots.txt` and the per-site delays are still respected | Measured on 16 real sites: 127 s one at a time against 22 s with 8 in parallel |
| S1 | Starting point | The search can start from an **address**, from **pasted coordinates** (for example copied from Google Maps), or from **latitude/longitude plus an azimuth and a distance** | Extends B6; still no map in the app |
| R1 | Rewrite in Go or Rust | **Evaluated and rejected** | See below |

### R1 - Why not rewrite in Go or Rust

A rewrite of the core in Go or Rust was evaluated for speed and rejected:

- CPU work (CV parsing, text extraction, scoring) is only about **7% of the search time**. The rest is waiting for the network and the politeness delays imposed by Nominatim, Overpass and the company sites.
- A faster language would therefore shorten the search by a few percent at most, while a full rewrite would cost weeks and lose the Python ecosystem used here (pypdf, trafilatura, fastembed/ONNX, the MCP SDK, Qt bindings).
- Running several sites in parallel (C1) attacks the real bottleneck and gives about **5x** (127 s down to 22 s on 16 real sites) without leaving Python.

Revisit only if profiling shows CPU time becoming a significant share of the search.
